# AI Code Review Task & Instructions

## 🎯 1. Цель (Objective)

Провести глубокий статический анализ исходного кода TODO-приложения на соответствие принципам **Clean Code** (модуль RS School). Помощник должен выступить в роли строгого, но конструктивного ментора, выявить скрытые проблемы читаемости, структуры и архитектуры, которые не ловит стандартный линтер.

## 🛑 2. Границы проверки (Scope & Boundaries)

- **Что проверять:** Логическую структуру функций, выразительность имён, отсутствие избыточного/шумного комментирования, дублирование бизнес-логики и правильное распределение зон ответственности (Single Responsibility) в файле `app.js` (или основном скрипте приложения).
- **Чего НЕ трогать:** Не предлагать изменения, ломающие текущую функциональность (добавление, редактирование, удаление и перенос задач должны работать). Не требовать установки сторонних библиотек или глобальной смены стека.
- **Важное ограничение:** Помощник **НЕ редактирует файлы напрямую**, он только анализирует код и объясняет проблемы.

## 🏁 3. Критерий готовности (Definition of Done)

Ревью считается полностью законченным, когда AI-помощник сформировал структурированный отчёт, покрывающий все проблемные зоны кода, и разложил каждое замечание по четырём обязательным пунктам Clean Code.

## 📊 4. Формат вывода (Output Format)

Результат анализа должен быть записан в файл **`review-report.md`** в корне проекта.

- **Язык отчёта:** Русский.
- **Структура:** Замечания должны быть сгруппированы по категориям из модуля Clean Code:
  1. Мёртвый код (Dead Code)
  2. Дублирование логики и обработчиков (Duplicated Code)
  3. Нечитаемые имена сущностей (Meaningful Names)
  4. Избыточные комментарии (Noisy Comments)
  5. Функции, которые не читаются целиком (Large Functions / Single Responsibility)

- **Каждое замечание строго должно состоять из 4 обязательных частей:**
  - **Место в коде:** Указание конкретной функции, переменной или номеров строк.
  - **Проблема:** Суть нарушения принципов чистого кода.
  - **Условие, при котором она проявляется:** Контекст, в котором этот код становится плохим или хрупким.
  - **Способ проверить исправление:** Конкретный критерий или шаг, как убедиться, что код стал чище (например, запуск тестов, проверка читаемости функции без скролла)
